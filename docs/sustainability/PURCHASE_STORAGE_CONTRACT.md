# Authenticated purchase integration contract — Phase 10

Status: repository interfaces, memory reference implementation and feature reset
boundaries are implemented. Authentication, verified sessions, durable storage,
network transport and backend authorization are **not implemented here**. This
contract describes behavior and domain fields, not a teammate's database schema.

## Domain data and ownership

`model.ts` exports PurchaseItem, VisitInput, NewVisitInput, Visit and validators.
Currency is integer USD cents; quantities are positive finite numbers (maximum
10,000,000) and units are kg/g/lb/oz/each/bunch/dozen/pint/quart/loaf. Limit each
visit to 1–100 items. Reject duplicate item IDs, invalid/future calendar dates,
unsafe/negative/fractional cents and item-price sums exceeding the trip total.

MarketVisit corresponds to the existing `Visit` projection:

- Visit ID: `submissionId` is the stable public visit address returned by this
  repository. The backend may use a different internal ID, mapped by its adapter.
- Authenticated owner: exclusively resolved from the verified server session.
  Store the ownership relationship server-side. **No owner/user ID belongs in
  NewVisitInput, form fields, client-supplied security checks or repository arguments.**
- Market ID: `marketId`, validated against the authoritative market directory on
  the server. Client selection alone does not establish existence or permission.
- Visit date: `date` in YYYY-MM-DD, a local calendar date, not a UTC timestamp.
- Submission timestamp: `submittedAt`, generated by server (memory uses its clock),
  never accepted as a client-controlled creation time.
- Total spending: `totalCents`, USD integer cents, once per trip.

PurchaseItem:

- Item ID: `id`, unique within its parent visit. The parent visit ID is the owning
  MarketVisit.submissionId in the nested repository representation; the server
  adapter must preserve the actual parent relationship in its chosen storage.
- Product: `product`, required name up to 120 characters; optional `productId`
  must name a current canonical food and match an exact recognized name/alias.
  Manual unknown names remain valid without an ID. Do not infer IDs by substring.
- Quantity and unit: required for **new writes** (NewVisitInput). Existing read
  records may lack quantity; VisitInput/validateVisit retain that historical
  compatibility. Never invent missing quantities during migration.
- Optional item total price: `spendingCents`, not a per-unit price.
- Optional vendor/farm: `vendor`, bounded self-reported text (200 characters).
- Optional production origin: `origin`, bounded self-reported text (200 characters).

Vendor/origin are optional and unverified. They never activate a local-grown flag,
local-spending fraction, freight distance, CO2e number or historical scenario.
Keep these private annotations separate from audited environmental evidence.

## Repository methods and semantics

`PurchaseRepository` in repository.ts is injected into PurchaseWorkspace:

- `persistence: 'memory' | 'authenticated'` describes the adapter. The memory
  implementation is tab-only development storage; the label is not proof of auth.
- `list(): Promise<Visit[]>`: all authorized visits for the bound session, stable
  chronological oldest-first order (submittedAt, then stable ID). The current
  dashboard reverses this order for newest-first display. Do not silently return
  a partial page: aggregate pagination in the adapter until a pagination-aware
  dashboard contract is agreed. Validate response integrity before returning it.
- `get(submissionId): Promise<Visit | null>`: retrieve one authorized returned
  visit ID; null for absent records. Never reveal another user's record.
- `submit(input: NewVisitInput): Promise<{ status: 'submitted' | 'duplicate'; visit: Visit }>`:
  validate again on the server, set owner/timestamp there, and return the canonical
  stored visit. An identical retry is duplicate, not a second trip. A different
  idempotency key with an identical trip fingerprint also returns duplicate.
- `delete(submissionId): Promise<{ status: 'deleted' | 'not-found' }>`: delete the
  addressed visit and all its items from that session's visible history. Repeated
  deletion returns not-found without affecting any other visit. Derived summaries
  must then be recomputed from remaining visits; do not retain orphan item evidence.
- `clear(): Promise<void>`: remove all visits/items visible to this session's
  purchase repository, **not** the account, profile, social data or another user's
  history. Define retention, audit and backups with the owner before deployment.

Deletion semantics include preventing retries of deleted submission IDs from
restoring a removed record. Keep an appropriate server idempotency tombstone for
its agreed retention window. A deliberate new submission key can record a new
visit after deletion. Memory tombstones last for the repository object's lifetime; deleted payloads
are discarded, retaining only retry keys and canonical visit addresses.
Clearing history is not the same as signing out or switching repositories.

`list/get/submit` return defensively isolated objects: caller mutation must not
alter future reads. No raw photographs, OCR fields, confidence, image URLs or
provider metadata are part of this contract.

## Atomic duplicate prevention

Do not implement deduplication as a separate unprotected select-then-insert.
Enforce owner-scoped submission-key uniqueness and fingerprint checks in one
backend transaction with concurrency protection. A reused key with a different
payload must fail. Compare all persisted annotations for same-key payload reuse;
trip fingerprint deduplication still uses market, date, trip total and sorted
product-name/quantity/unit/item-price tuples, excluding annotation differences.
This deliberately preserves the existing duplicate-trip behavior and never
silently overwrites the first recorded trip's annotations. Persist the canonical
acknowledgement and apply deletion retention policy to retry aliases too.

Quantities, cents, IDs and strings must be validated server-side even though the
browser already runs validateNewVisit. Do not trust a client-computed fingerprint,
product ID, timestamp or owner. Rate limiting/retention and authorized deletion
must be implemented by the backend owner in the existing account infrastructure.

## Session lifecycle and UI injection

`PurchaseSession.purchases(): Promise<PurchaseRepository | null>` is an integration
seam only. The auth owner must derive identity from their verified session, issue
a fresh stable repository object for each account/session epoch, and immediately
pass null/unmount the workspace when signing out, expiring or changing accounts.
Do this before awaiting the next session/repository request. Discard a late result
from an older session; do not briefly display it during an account switch.

- Inject a repository using `<PurchaseWorkspace markets={markets} repository={repo} />`.
- Passing undefined intentionally selects the labelled development memory fallback.
  Do not use undefined during authenticated loading or sign-out.
- Passing null renders a disconnected state and unmounts all purchase UI/history.
  It does not silently downgrade to a memory account.
- Repository identity changes key a fresh private workspace, clearing drafts,
  loaded history, pending UI feedback and selected environmental scenario.
  An identity key is a reset boundary, **not server-side access control**.
- Do not repurpose one mutable repository object for multiple accounts. Remove it
  on logout and clear any adapter caches. A memory object intentionally retains
  its demo records while referenced; owner lifecycle must discard private caches.
- All list/get/delete/clear/submit operations must verify session and authorization
  at the backend for that operation. Enforce RLS/equivalent ownership constraints.

Use `PurchaseRepositoryError` codes session-expired, forbidden and unavailable
for safe structured failures, without exposing raw upstream messages. Expired
session errors in current list/submit/clear UI lock the workspace and clear its
private view. Reconnect with a new session-bound repository. Backend requests
must reject expired/revoked sessions even if an old UI request remains in flight.

Temporary network/save failures preserve the confirmed form and submission key
for retry. History loading failures expose a retry without clearing the draft.
If the server committed but the response was lost, retry the same submission key
and original payload. Editing a payload that might already have been saved must
not overwrite it: same-key conflicts must be surfaced, then reconciliation may
fetch the stored visit before a deliberate new submission. Do not log private
purchase text or raw responses as error diagnostics.

## SustainabilitySummary projection

`impactSummary(visits, evidence)` remains the source of dashboard values:

- `visits`: one trip per deduplicated submitted visit.
- `uniqueMarkets`: count distinct market IDs.
- `marketSpendingCents`: sum trip totals exactly once (do not add item prices again).
- `localSpending`: evidence-based estimated local spending Metric.
- `foodMiles.weightedDifference` and `foodMiles.averageDifference`: existing
  recorded-mass calculations with sourced local/conventional distances.
- `transport`: existing supported EPA-factor transportation CO2e difference Metric.
- `lifecycle`: unavailable without compatible, paired stage/boundary LCA evidence.

Every Metric preserves value/unit, knownSubtotal, quality, covered/expected,
methodVersion, sources, assumptions and missing information (see evidence.ts for exact types). Keep evidence/provenance separate
from self-reported purchases and expose missing-data warnings. A current or
historical scenario is never a measured individual-purchase impact by default.
Historical Syracuse comparisons still require explicit opt-in and geographic,
product, date, season and mass eligibility. No formulas or adapters change here.

## Owner acceptance checks before enabling persistence

Verify real authentication and account ownership with two users, cross-user
get/delete/list denial, expired/revoked sessions, late responses during logout,
row ownership and parent-child integrity, server validation, concurrent duplicate
submissions, changed payloads, deletion and retry retention, pagination ordering,
currency precision, failure recovery, durable reload, retention/deletion and
cache clearing. Current memory/unit UI tests demonstrate contract behavior only;
they cannot certify backend authentication, authorization or durable storage.
